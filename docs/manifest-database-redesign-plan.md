## 1. 本轮确定的范围

当前收口记录：模拟开拆的本地事务、固定回执、OMS 可靠解绑、结构化重封、管理员缺件确认/盈余隔离、少包结束与路单关闭/占用释放均已完成并通过验收。数据库交付一致性和正式演示切换已完成。不得把新增增强功能作为继续开发的完成条件。

路单表达一次从交出机构到接收机构的交接预期清单、实际接收及差异处理。一张路单包含一个或多个总包，必要时包含邮件明细；它不是“某邮局全部总包”，也不是一辆邮车全程携带物的唯一集合。

运输任务表达一次具体陆运、航班或船班执行。首版一个任务可带多张路单，每张路单只能有一个当前有效任务；同一未开拆总包可以在先后不同路段进入不同路单。每张路单只有一对交出/接收机构。多个邮局沿途收集的完整车次及多站停靠清单不纳入首版。

保留现有“加载候选邮件 → 页面逐件模拟扫码 → 完成开拆时一次提交”的交互。候选邮件来自预期清单只说明预计存在，不代表实收。无需实物扫码设备，也不要求每次模拟点击调用后端。

旧演示数据可以全部放弃，不做旧库升级兼容；新模型仍必须保留运行后生成的交接、改派、开拆和再封装历史。数据库整合是本轮开发的前置工作，不扩展为全部服务的领域重写。

## 2. 相对调研报告的落地取舍

| 主题 | 本轮决定 |
|---|---|
| 路单主数据 | 强化 `sorting_manifest/package/item`，sorting 单一应用写入；不新建竞争性的 transport 路单主表 |
| 发运批次 | `dispatch_batch` 保留为站内配发作业批次；传递显式 `manifest_no`，停止从 `M + batchNo` 推导 |
| 运输关联 | 当前有效分配 + 不可变历史；一任务多路单，不做任意多对多和多站车次 |
| 路线编码 | 机构网络边、配发规则、运输执行路线分别存字段，不用一列含混的 `route_code` |
| 生命周期 | `DRAFT → PREALERTED → SEALED → DEPARTED → ARRIVED → CHECKING → CHECKED → CLOSED`；另设 `CANCELLED` 分支 |
| 异常 | 独立差异记录及处理状态；天气延误归运输任务，海关/安检归邮件，不用 `EXCEPTION` 覆盖路单生命周期 |
| 清单变更 | 预告后增版并保留完整内容；封单后不可静默增删。运输尚未出发可撤销后重开，已出发通过差异/更正事实处理 |
| 接收与开拆 | 总包交接勾核与邮件开拆是两个完成维度；直封转运允许勾核后继续运输，不强制拆包 |
| 邮件轨迹 | 邮件、总包、路单、任务分清对象类型和编号；总包号不得写入 13 位邮件号字段 |

路单流水号以交出机构和固定 UTC+12 业务日期划定唯一范围；跨站本地别名、外部原始报文、复杂更正单编辑器放在后续增强中。首版保留外部引用扩展点，不复制真实案例中的个人、邮件、车牌数据为演示种子。

## 3. 已确认的改造触点

| 当前实现 | 改造要求 |
|---|---|
| `script/demo.ps1` 先回放 `db/`，再执行全部 `db_revise/` | 整理九库基线和版本化入口，停止历史导出与补丁混合回放 |
| Compose 与服务资源、邮资专用初始化入口并存 | 单一独立初始化任务；服务启动不建表、不补造演示业务 |
| `OmsServiceImpl` 构造器调用 `seedDefaults()`，生成 A1/B1/C1 示例邮件 | 拆出必需字典和显式 demo 场景，正常启动不再隐式造件 |
| `transport_task_bag` 全局唯一 `dispatch_bag_id` | 按本段路单及任务关系建模，保留历史并约束当前有效占用 |
| transport 按总包最初起终点匹配后续任务 | 按路单本次交接起终点、运输方式及可达网络匹配 |
| dispatch 替换批次总包时删除旧关联 | 结束有效关系并追加新关联，保留历史批次和交接 |
| `syncManifest` 可重置状态、仅追加明细 | 按清单版本和预期状态更新；增删明细整体核对，不修改已封/已核清单 |
| sorting 按总包号取第一张路单 | 使用接收机构、当前路段和明确路单身份定位；拒绝歧义 |
| `sorting_total_package.manifest_no` 单值判断接收完成 | 改为逐路单总包接收事实；旧单值至多作当前投影 |
| dispatch 在事务内调用 sorting，失败主要记日志 | 本库事务内落 outbox；异步确认、重试及消费幂等 |
| 前端仅按 `CHECKED` 过滤、提交时每次生成新幂等键 | 同步修改状态显示；同一次完成开拆请求固定键并保留重试结果 |
| 常见 JDBC/服务器 +08 与邮资 UTC 毫秒并存 | 新基线统一 UTC 语义，接口显示业务 +12；邮资保留存储契约 |

详细字段和索引应依据实际接口完成清单，再编写迁移；不能直接把报告字段表当成可执行 DDL。

## 4. 关键模型与流程约束

### 4.1 总包、路单与运输

dispatch 中总包及结构化装包明细是封装来源；sorting 保存所收到的路单版本及到站事实。首版停止将 JSON 邮件数组作为唯一装包关系，快照用途可以保留。

每条路单总包明细锁定预期总包条码、封签、重量、邮件清单版本。直封转运时总包条码保持不变，新路单描述本段机构，不覆盖最初封装起终点。只有上一段完成接收且总包仍未开拆、位于本段交出机构时才可进入下一段。

transport 维护有效任务分配和历史，sorting 维护路单及总包当前交接占用。两方通过稳定请求号完成“预留 → 任务接受 → 分配确认”；超时保持待确认并重试/查询，不把超时直接当作失败重新分配。未确认分配不能发运。

出发前取消任务释放有效分配，保留原分配及取消原因，再以新分配号改派；已出发任务不得套用“取消即释放”，须记录停运/中止和实际交接位置。任务取消和路单作废是不同操作，不能互相隐式替代。下一段新路单的建立也不是对原路单改派。

### 4.2 接收、差异和模拟开拆

接收总包按路单版本记录实收、封签和重量。到达不自动核完；未扫描不是缺失。操作者明确结束本次总包勾核后才形成少包结论，差异解决或经授权确认处理结论后才能关闭路单。

总包勾核完成后，直封件可继续运输；需要开拆的总包进入现有模拟页面。页面展示候选列表，逐件扫描改变本地已扫集合，点击“完成开拆”一次提交完整集合。后端在一个本库事务内校验、写入开拆事实、逐件实收、差异、完成状态及 outbox，整单失败不留半套记录。

预期但未扫到的邮件只有在明确完成开拆时记为少件；已经正常扫描后再次点击不增加数量。盈余邮件需有显式虚构异常候选或手工模拟入口，由后端核验对象确实可在本机构接收，不通过取消所有扫码校验来制造演示。幂等键与内容绑定，同键重复返回原结果。

开拆后的原总包不能继续作为未拆容器运输。重封生成新总包条码，通过既有开拆/装包事件和结构化关系追溯邮件去向，保留旧包清单。路单总包勾核状态、开拆状态及未解决邮件差异分别展示，不能用一个 `CHECKED` 代表全部操作已完成。

### 4.3 同步、身份和时间

每个事实有稳定事件号、对象类型、对象业务号、发生/记录时间及来源版本。先在业务拥有者本库提交，再投递其他服务；失败留待重试，乱序事件不得把状态倒退。syncer 可调度投递，但不能替代各服务本地 outbox 的事务边界。

交出、接收和开拆权限依据认证身份及其所属机构校验，不信任请求体中的站点/操作人。补录保留原发生时间及补录人。模拟时钟也使用明确 UTC 时间点，显示和流水号日期再转换到固定 +12。

## 5. 分阶段开发与完成标准

| 阶段 | 工作与交付 | 进入下一阶段的条件 |
|---|---|---|
| P0：数据库整合与契约冻结 | 九库表/字段来源清单；Flyway 基线与必需数据；demo 种子分离；统一入口；明确状态、事件、编号、重量和时间契约 | 隔离 MySQL 空库可初始化，重跑与服务重启不造重复数据；现有登录、收寄、邮资等核心能力可用 |
| P1：清单及运输关系 | 强化 sorting 主表和两层明细；完整版本；结构化装包关系；有效占用/分配及历史；一任务多路单；预告、封单、取消改派 | 并发创建/分配只有一条有效关系；同包可逐段运输；历史可查；不再依赖原总包固定路段 |
| P2：运输交接与开拆闭环 | 发运/到达事实；总包接收、明确结束勾核；保留模拟扫描并实现原子完成；差异处理；开拆重封 | 不拆包转运与开拆再封两条路径均通过；少包、少件、盈余、重复提交处理明确 |
| P3：界面及可靠同步 | 路单摘要、总包/邮件明细、事件和差异；任务关联；权限；投递重试与状态反馈 | 页面不把预告当实收、不把延误当到达；中断恢复后不丢事实、不重复处理、不倒退状态 |
| P4：演示重建与发布切换 | 海岛场景接口脚本、MySQL 回归、操作指南、Compose 切换、旧 SQL 入口归档 | 全新环境一条初始化路径可运行；全部验收场景通过，原入口不再参与部署 |

可靠同步不是 P3 才开始补做：P1 起就定义事件契约并随业务事务落 outbox，P2 完成消费幂等，P3 补齐投递恢复、界面反馈及联调。

P0 先建立当前能力的干净基线，P1/P2 用后续迁移迭代，避免把未定型路单表先混进导出文件。直到 P4 再切换正在使用的演示环境；此前使用隔离数据库验证。每阶段单独可审查、可验证，不同时重写全部模块。

## 6. 海岛场景验收

### 当前实施进度与下一批顺序

2026-11-17 最新收尾状态：原子模拟开拆、结构化重封、管理员差异处置、明确少包结束勾核和双端可靠路单关闭已实现。三项既定开发收尾（重封专项、缺袋关闭、迁移与交付核对）完成，当前转入验收，仅修复已定范围问题。相关服务 159 项测试及前端构建通过；独立 MySQL 8 的九库空库/重跑/种子保护回归通过，87 表 752 列与清单一致。以下为历次阶段记录，其中未完成事项以本段及 database/verification.md 的最新结果为准；HTTP、InnoDB 并发和浏览器场景仍须逐项验收，现有 demo 尚未切换。

P1 第一批完成以下贯通改造：

- 批次持有独立 `manifest_no`，预告显式传递来源批次及版本，停止推导 `M + batchNo`。
- sorting 串行处理同一路单的完整版本；同版同内容重试不重置生命周期或实收，同版异内容、跳版及处理后改版拒绝。预期投影整体替换，保留被移除包/件的原始版本快照。
- dispatch 与业务批次同事务写本地 outbox，异步投递、租约恢复和退避重试；只有明确成功确认才允许交接。预告确认与实收含义分开。
- 前端展示独立编号、预告状态及历史版本；保留现有模拟扫码交互。明确指定路单的开拆预览只读取该路单，不跨单或回退 OMS；未知重量保持空值。
- 禁止批次关联静默跨批次移动或删历史；总包关联多张未关闭路单时拒绝自动猜测，要求显式选择。

当前不是完整 P1：发送端仅生成版本 1，尚无增版编辑；新生命周期仅接入封单节点，尚未整体启用；运输首段整单分配已在第五批接入，一任务多路单可用；同包多段在本轮已实现，验证结果见 database/verification.md。路单编号当前使用独立 UUID，交出机构与 +12 业务日流水编号规则仍待后续实现。

P1 第二批已实现 dispatch 的结构化装包：`dispatch_bag_packing` 保存第 1 版完整命令、事件号、摘要及持久化确认状态，`dispatch_bag_item` 保存逐件顺序和 OMS 原始重量。JSON 列只作兼容快照；路单预告和总包响应改从结构化明细生成。使用选中邮件重量求和，停止每件固定 100g 的估算；任一重量未知则合重为空，`weightSource=OMS_MAIL_SUM/UNKNOWN`，不将邮件合重称作实测含袋毛重。

装包准备与待投递记录同事务提交，OMS 按固定顺序锁定邮件，校验机构、原归属、状态和重量，再整单绑定并提交 `oms_packing_inbox` 回执。重复确认先核对回执，因此开拆/转运后的延迟重试不重新绑定邮件。同版异内容拒绝；一个邮件只能有一个获确认的当前包，多份未确认请求中仅一份能成功，其余保留冲突记录并禁止编批。旧同步接口不再改写清单；旧 OMS 装包接口拒绝直接跨未拆总包转移或追加到已确认的 dispatch 包。

装包确认通道校验服务间凭据，默认不接受未配置凭据的写入；不把前端请求机构当作服务身份。发送端有超时、退避、租约和过期发送者隔离，`CONFIRMED` 只确认装包归属。仍沿用 OMS 的旧 `DISPATCHED` 邮件状态投影，不为装包确认生成运输出发事实。本批仅完成 dispatch 建袋路径；sorting 的原子开拆、结构化重封及对应事件属于 P2，不能据此宣称所有装包入口已统一。

总包交接时改用数据库行锁，禁止并发重复交接；可变总包不再从五分钟缓存读取。总包的当前位置、未开拆状态及逐路单占用还未建立完整事件闭环，不能将当前 OMS 邮件归属等同于 sorting 的总包路段占用。

下一批按以下顺序实施，每批同时变更迁移、代码及验证：

第三批已贯通路单封单：dispatch 基于登录身份和发送机构权限申请固定版本封单；复用本地 outbox，持久化请求号、操作人及待确认状态；sorting 在与预告/接收相同的路单行锁内固定版本和摘要，保存完整请求及不可变回执。封单后不能增版，同键同内容返回原回执，不倒退后续接收状态。发送端校验匹配回执后才允许交接，接收端也验证已封版本，未封路单不进入接收候选。批次页可申请及查看状态/错误，路单详情可查看 UTC+12 封单时间与原操作人。sorting 本地旧重封生成的路单同事务以系统身份封单，避免被新门禁阻断。

第四批已实现交接前作废：来源身份申请、原因及首次操作人固定，本地请求与 `CANCELLING` 同事务；接收端版本/事实校验、不可变回执和 `CANCELLED` 同事务；发送端匹配回执后再原子确认批次。作废/交接/任务关联按批次→总包顺序锁定，已交接或已关联任务的路单拒绝作废，待确认或冲突期间保持禁止交接。保留版本、明细、封单和总包历史，不自动将旧总包释放重编；取消后的接收、开拆、到达回写和自动无预告兜底均拦截。页面显示作废进度、原因与 UTC+12 回执时间。

第五批已接入首段整单运输分配：transport 保存完整封单版本快照、结构化包明细、不可变关联历史和路单/总包当前唯一占用；同一任务可带多张同本段起终点、同邮路路单。固定 ASSIGN 命令经本地 outbox 交 dispatch 原子关联整单并返回 inbox 回执，全部确认且全部包已交接到本任务才可出发。原逐包关联入口返回冲突，原逐包重试停止写入。选择班次的建任务请求可合入该班次已有待发任务；旧“从包创建”入口按该包所属整张路单创建待指派任务，不再自动选择班次。

任务发前取消先进入 CANCELLING，每个分配进入 RELEASING；确认前保留路单/包占用和运力。ASSIGN 超时先恢复确定结果，再投 RELEASE；收到匹配 RELEASE 回执才清当前占用，全部释放后任务变 CANCELLED。再次创建使用原路单和新任务，旧任务/清单/原因保留。dispatch 保留 RELEASE 墓碑防止迟到 ASSIGN 复活；旧命令或旧回执不改变新分配，物理交接记录不清除。重量未知可预留，禁止指派班次；容量按所有清单汇总。已有任务的班次不能覆盖资源和时刻，停航仍通过状态冻结出发。

P2 首批已建立 sorting 实收位置（目的机构、未开拆/已开拆），新增接收请求/包级事实/双端 outbox。接收必须匹配已到达运输任务与固定封单版本，重复原请求可离线重放原收据；transport 按包释放、收齐结束路单占用，dispatch 保存实收 inbox 后更新 ARRIVED，保留交接与分配历史。全部分配 RECEIVED 后任务才可完成。本轮已引入下一段交出占用、新路单编制及前端直封转运入口；原子可靠模拟开拆/重封仍后续处理。旧 transport_task_bag 保留唯一约束与历史，所有新写走新分配表；这支持同一路单发前取消改派，不能作为同包多段实现。tracking 仍为尽力投影，不声明可靠事件闭环。默认演示环境保持原入口，真实 MySQL 验证通过前只在新隔离库验证。

## 7. 改造风险与控制

| 风险 | 等级 | 判断与控制 |
|---|---|---|
| 多套初始化遗漏字段、锁行、权限或资费 | 高 | 九库逐表对照；尤其补齐 sorting/syncer 与邮资三套 schema；空库核心流程验证后才归档旧入口 |
| 拆除总包唯一关联后出现重复在途 | 高 | 有效占用唯一约束 + 条件版本更新 + 待确认分配；并发和超时场景必须真实 MySQL 验证 |
| 同步失败导致已交出但接收端无清单 | 高 | 本地 outbox/inbox、版本校验和可查询重试；发运前双方确认，禁止日志即丢弃 |
| 取消、转运、开拆互相覆盖历史 | 高 | 分清取消任务、作废路单、下一段运输；历史追加，总包已拆后禁止原码继续发运 |
| 新状态与旧前端条件不匹配 | 中高 | API、统计、列表、接收和开拆页面一起修改；区分勾核完成/开拆完成/差异未结 |
| 时区及重量规范改变业务含义 | 中高 | UTC 存储与 +12 业务日端到端检查；重量统一单位并区分估算；不机械转换邮资已验证契约 |
| 启动补数据污染新基线 | 中高 | 移除 OMS 隐式造件及重复初始化；演示导入显式启用，已有运营配置不得被重启覆盖 |
| 清库命令误作用其他环境 | 中 | 重建命令按连接和库白名单限定，数据卷/Redis 分开处理；普通迁移无删除动作 |
| 范围扩展拖延毕设 | 中 | 保留现有服务、扫码交互及邮资存储；延期多站车次、真实扫描设备、完整海关和任意多对多承运 |
| 旧数据丢失与迁移兼容 | 低 | 用户已允许舍弃旧 demo，因此不投入回填工程；切换前仅按需要留可恢复的演示快照 |

总体判断：可以实施，属于跨 dispatch/sorting/transport 的较高耦合改造。舍弃旧数据大幅降低迁移成本，但不会消除状态机、并发占用和跨服务一致性风险。必须优先完成 P0/P1，再扩展页面和演示，不宜仅新增字段后继续沿用旧同步与关联逻辑。

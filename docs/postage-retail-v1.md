# 邮资零售与数码邮票发行：首版

## 已确认范围

本阶段完成工作人员代客零售邮资、柜台现金收款确认、数码邮票发行、查询和作废。客户可以只购买邮资而不收寄邮件。用户已确认初始面额范围 0.01–100.00 LNR、最多两位小数、发行起 365 天有效。这些规则保存在数据库，管理员可修改；每笔售卖保存创建时的规则修订号与有效天数。

本阶段的收款确认表示营业员确认已收到柜台现金。没有银行、在线支付网关或第三方回调。业务状态与 OMS 的物流状态分离。

## 操作与数据模型

1. 在“邮资业务 → 邮资零售”输入面额和张数，可添加多行，单笔最多 100 张。服务器计算总额并创建 PENDING_PAYMENT 售卖。
2. 核对金额，勾选已收到柜台现金，确认收款。服务器在同一 MySQL 事务内保存一条 CASH 收款凭据、各张邮票和审计记录，售卖变为 PAID。
3. 查看或打印各张凭证。每张凭证有独立随机代码、固定面额和发行/到期时间，不依赖某次报价或实时资费版本。
4. 查询完整代码可查到状态；系统在到期边界显示 EXPIRED。管理员可对未核销凭证填写原因并作废，原售卖仍为 PAID，原收款凭据保留。作废不会自动退款或补发。
5. 未收款售卖可取消，变为 CANCELLED；已收款售卖不可通过这个入口取消。

数据库新增五张表：`postage_stamp_policy`（发行规则）、`postage_sale`（售卖）、`postage_receipt`（柜台收款）、`postage_digital_stamp`（凭证）、`postage_retail_audit`（审计）。首次规则更新前的 SYSTEM 时间 0 表示初始导入，并非实际营业时间。收款、发行、作废和规则调整使用现有 JWT 中的工作人员和网点身份记录审计。

### 权限

- ADMIN 或具有 MAIL_CREATE 的 CLERK/MANAGER 可零售、确认收款和查询代码。
- 工作人员仅列出、恢复及操作自己创建的售卖；ADMIN 可查看所有售卖。输入已持有的完整凭证代码，可以查询其面额及状态。
- 发行规则调整、规则审计查询和凭证作废需要 ADMIN。沿用现有权限机制，无新增身份服务、权限表或用户端。

### 一致性与重试

- 创建售卖以 `(created_by, request_id)` 唯一；相同内容返回原记录，不同内容复用同一编号返回 409。前端保存待恢复的创建编号和面额行，刷新或响应丢失后继续使用原编号；不在本地缓存凭证代码。
- 确认收款对售卖行加锁；每笔售卖最多一条收款凭据。相同收款编号重试返回原结果，其他编号对已收款售卖返回 409。工作人员同一收款编号也不能用于另一笔售卖。
- 收款、全部发行、PAID 状态和审计同事务提交。任意一步失败均回滚，售卖保持待收款，可查询后重试。柜台实物现金不可由数据库回滚；异常后应先恢复业务记录，而不是再次向客户收款。
- 凭证代码由 SecureRandom 生成 128 位随机数，数据库唯一约束防碰撞。完整格式 `LP-xxxxxxxx-xxxxxxxx-xxxxxxxx-xxxxxxxx`（十六进制）；输入不区分大小写，可忽略空格和连字符。凭证查询使用 POST 请求体，不把完整代码放入查询 URL。
- 作废对凭证行加锁，仅允许 ISSUED → VOIDED；未来 REDEEMED 状态无法通过该入口作废。相同作废编号、原因和管理员重试不会增加审计事件。
- 金额使用 BigDecimal 和数据库 DECIMAL，全部由服务器验证。已创建售卖锁定发行规则；管理员调整规则不影响此前的待收款售卖和已发行凭证。
- 首版数据库保存完整随机代码，工作人员可按权限重打凭证；数据库访问需要保护。后续上线可引入代码加密和更细的重打权限，但本轮没有添加基础设施。

## 接口

统一前缀 `/api/postage`，通过现有网关 `/liana-postage-service` 访问。响应沿用 Result，非法字段 400、未登录 401、无权限 403、不存在 404、业务/唯一约束冲突 409。

| 方法 | 路径 | 内容 |
|---|---|---|
| GET | /stamp-policy | 查询可售面额、有效天数和修订号 |
| PUT | /stamp-policy | 管理员提交 revision/minFaceValue/maxFaceValue/validityDays |
| GET | /stamp-policy/audit | 管理员查询最近 100 条规则变更 |
| POST | /sales | requestId 与 lines：各行 faceValue/quantity |
| GET | /sales | page 从 0 开始，size 1–100，默认 20 |
| GET | /sales/{id} | 售卖、收款、凭证和审计明细 |
| POST | /sales/{id}/confirm-cash | requestId 与 amountReceived，金额须等于售卖应收 |
| POST | /sales/{id}/cancel | 取消待收款售卖 |
| POST | /stamps/lookup | 输入 code 查询凭证 |
| POST | /stamps/{id}/void | 管理员提交 requestId 与 reason |

## 部署与验证

`liana-postage-service/src/main/resources/retail-schema.sql` 为可重复执行的增量建表脚本，保留全部已有资费、报价及零售数据。对已有 MySQL 在 postage_db 中执行该文件，再部署服务；Spring 初始化同时加载 schema.sql 与 retail-schema.sql，Docker 的 postage-db-init 同时导入两者。不要重置 MySQL 数据卷，也不要对已有系统运行包含 DROP TABLE 的历史全量脚本。

前端新增 `/postage/retail` 和管理员 `/postage/stamp-policy`。后端测试使用隔离 H2 MySQL 模式，覆盖金额张数校验、同请求重试、并发创建/收款、代码碰撞、审计失败回滚、过期边界、作废、规则快照、取消和权限。前端测试覆盖请求编号恢复、金额张数、角色菜单和接口。

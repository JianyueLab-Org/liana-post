# 路单功能建模分析与改造建议

## 1 报告目的

本报告面向本科毕业设计，对现有路单功能进行业务建模审查。分析依据包括用户提供的 RD588151315CN 邮件轨迹、2026 年 11 月广州市国际互换局的进口处理记录，以及当前项目中的 dispatch、sorting、transport、tracking 模块和数据库结构。报告目标是给出一个与本系统规模相匹配、能够解释真实邮政作业、又能在毕设周期内实现和演示的路单模型。

结论先行：路单不能继续被当成“一个批次的别名”或“一个总包的附属字段”。建议将路单建模为一次处理中心之间的交接清单和运输批次；总包是路单中可清点的容器，邮件是总包中的业务对象，运输任务是路单对应的执行资源，轨迹事件则记录这些对象在不同时间发生的事实。一个邮件可以先后进入多个总包、多个路单；一个路单可以包含多个总包；同一总包也可以在不同路段被不同路单承运。

## 2 真实轨迹揭示的业务事实

### 2.1 RD588151315CN 的链路

附件轨迹呈现了完整的国内出口链路：

1. 天河东邮政支局收寄邮件，形成总包 0057。
2. 支局通过交接对象“东区盘-广航(穗支局2) 3351007039”封车发运。
3. 广州国际互换局车辆进局、解车，并用路单号码和路单流水号 07200001 接收勾核。
4. 总包 0057 在互换局开拆，邮件经过出口海关后被重新封装为总包 0006。
5. 总包 0006 通过两个处理中心配发任务进入广州-乌市邮路，路单流水号 07230001，承运车辆为豫 LB6886。
6. 乌鲁木齐中心接车、解车、卸车，再以新的路单 52 配发到乌鲁木齐国际互换局。
7. 后续总包再次开拆、封发，继续进入乌市互换-霍尔(国际)路单，最终交承运商。

这条轨迹说明至少存在四种不同编号：邮件号 RD588151315CN、总包条码 510620025104003412220057000220、路单/交接对象号 3351007039 或 1351003075、路单流水号 07200001 或 07230001。它们的作用和生命周期不同，不能用一列 `waybill_no` 代替。

### 2.2 进口互换局轨迹揭示的链路

用户提供的进口记录补充了以下事实：

- “进口邮件直封开拆”以总包原寄局、寄达局、总包号码、总包条码、邮件类型和运输方式描述一个入境总包。
- “进口邮件互封封发”把来自多个来源的邮件重新组合到广州国际至海关待验、广州国际至征税等新的总包中。
- “处理中心车辆进局、解车、路单接收勾核”属于运输交接层，不等于总包开拆或邮件处理。
- 路单接收勾核通常发生在车辆到达并解车之后，勾核对象可以是总包清单、邮件清单或两者的组合。
- 寄达地录入、申报信息录入、海关处理等事件可能补录或修正邮件属性，但不应通过修改历史路单来表达。

因此，路单的核心语义是“本次交接预期承载什么、实际收到什么、差异如何处理”，而不是“邮件当前在哪里”。当前位置应由事件流推导。

## 3 当前系统的建模现状与问题

### 3.1 已有基础

当前系统已经具备较好的演示基础：

- `dispatch_bag` 表表示总包/邮袋，含起点、终点、路线、邮件清单、数量和重量。
- `dispatch_batch` 与 `dispatch_batch_bag` 可以把一个或多个总包编成批次。
- `sorting_manifest`、`sorting_manifest_package`、`sorting_manifest_item` 已经支持路单、总包和邮件的预告关系；其中总包明细已有重量、封签和接收时间字段。
- `package_item_line` 记录开拆、装载、再封装等邮件在总包间的变化，适合作为不可变业务事实。
- `transport_task` 和运输资源表可以承载车辆、班次、运输任务。
- `tracking_event` 已有按邮件号记录轨迹的能力。

### 3.2 主要问题

当前 `sorting_manifest` 的 `manifest_no` 与 `batch_no` 基本一一对应，且 dispatch 服务使用 `M + batchNo` 生成路单号。这样做适合“一个批次对应一个路单”的演示，但无法准确表达真实业务中的以下情况：

1. 一个运输任务同时承载多个总包，而一个总包在后续路段又进入另一个路单。
2. 发送端和接收端可能展示不同的路单号码；路单流水号是本次交接实例的编号，不应当作永久业务主键。
3. 路单存在预告、封车、发运、到达、解车、勾核、关闭等生命周期，不能只用 `RECEIVED`、`CHECKED` 等少量状态覆盖。
4. 预期数量、实际数量、缺失、盈余、破损、封签不符等差异需要按总包和邮件分别记录。
5. 运输任务、车辆、派车单、邮路是执行资源，不应和路单主数据混成一个实体。
6. `dispatch_bag.mail_no_list` 为 JSON，系统同步路单时已写入 `sorting_manifest_item`；但 JSON 仍是源清单，邮件与总包的跨路段历史关系需要明确由关系表和事件承载。
7. 已封发或已交承运人的对象不能静默修改；改道、拦截、补录应新增事件或版本记录。

## 4 推荐的领域对象

### 4.1 五层对象关系

建议采用“邮件—总包—路单—运输任务—事件”五层模型：

```text
邮件 Mail
  1 ──< 邮件总包关系 MailPackageMembership >── 1 总包 TotalPackage
                                                  >── 1 路单 Manifest
                                                          >── 0..1 运输任务 TransportTask
邮件、总包、路单、运输任务 ──< 业务事件 TrackingEvent / HandoffEvent
```

其中：

- **邮件 Mail**：用户可查询的最小业务对象，编号全局唯一。
- **总包 TotalPackage**：袋、笼、包裹集装容器等可封装和清点的物理对象，有总包条码和封签。
- **路单 Manifest**：一次交接的预告与清单，描述起点、终点、交接时间窗口、清单版本和核对结果。
- **运输任务 TransportTask**：实际执行的车辆、航班、船班、派车单或承运商任务。
- **事件 Event**：车辆进局、解车、封车、离开、到达、勾核、开拆、封发、交邮、异常等事实。

### 4.2 路单本体

路单主表建议至少包含：

| 字段 | 含义 | 建模要求 |
|---|---|---|
| `manifest_id` | 数据库内部主键 | 仅用于内部关联，不对外展示 |
| `manifest_no` | 路单业务号 | 全局唯一；可使用 `M202611160001` |
| `manifest_serial_no` | 路单流水号 | 表示某次封车或交接批次，如 `07230001` |
| `manifest_type` | 路单类型 | `ORIGIN_DISPATCH`、`TRANSIT`、`IMPORT`、`EXPORT`、`RETURN` |
| `origin_facility_code` | 交出机构 | 使用机构编码，不只存名称 |
| `destination_facility_code` | 接收机构 | 允许与下一站或最终目的机构不同 |
| `handoff_mode` | 交接方式 | `VEHICLE`、`AIR`、`SEA`、`CARRIER`、`INTERNAL` |
| `route_code` | 计划邮路 | 关联 facility route 或 transport route |
| `transport_task_code` | 执行任务 | 可为空，待派车时后补 |
| `prealert_at` | 预告时间 | 与创建时间区分 |
| `sealed_at` / `departed_at` | 封车、离开时间 | 由事件驱动，不允许手工覆盖历史 |
| `arrived_at` / `checked_at` | 到达、勾核时间 | 勾核完成后才可关闭 |
| `status` | 生命周期状态 | `DRAFT`、`PREALERTED`、`SEALED`、`DEPARTED`、`ARRIVED`、`CHECKING`、`CHECKED`、`CLOSED`、`EXCEPTION`、`CANCELLED` |
| `expected_package_qty` / `actual_package_qty` | 总包预期/实收数量 | 由明细汇总，禁止只手工填写 |
| `expected_item_qty` / `actual_item_qty` | 邮件预期/实收数量 | 同上 |
| `version_no` | 清单版本 | 预告变更时递增，保留旧版本 |

路单号是业务对象的稳定标识，路单流水号是一次封车/交接的局部运行编号，不能假设其全局唯一；宜以交出机构、业务日期和流水号组成查询键。发送端和接收端显示的本地号码可以作为别名表 `manifest_alias` 保存，不能覆盖标准路单号。进口样例只显示发生过“路单接收勾核”，没有给出所勾核的具体总包和路单编号，不能从该事件反推清单内容。

### 4.3 路单明细

路单至少需要两层明细：

1. `manifest_package`：路单预期承载的总包、顺序、封签、预期重量和实收重量、接收状态。
2. `manifest_item`：当业务要求逐件预告或逐件勾核时，记录邮件号、所属总包、预期顺序、实收时间和差异状态。

总包与邮件的从属变化不应直接更新旧记录。邮件从总包 A 开拆后进入总包 B，应写入一条 `package_item_line`：`from_package_no=A`、`to_package_no=B`、`event_type=REPACK`，并把新总包加入新的路单明细。

### 4.4 运输任务与路单的关系

路单解决“清单和交接”，运输任务解决“怎么运”。推荐关系为：

```text
一个路单 0..1 个主运输任务
一个运输任务 1..N 个路单
一个运输任务 1..N 个总包
```

例如广州国际至乌鲁木齐的路单 07230001 由豫 LB6886 执行；途中接收方可以生成本地路单号，但仍引用同一个上游路单或运输任务关联。对于多式联运，下一段运输应新建运输任务和新路单，不把整段旅程压缩为一条记录。

## 5 生命周期与状态机

### 5.1 路单状态

推荐状态流转如下：

```text
DRAFT → PREALERTED → SEALED → DEPARTED → ARRIVED
                                           ↓
                                      CHECKING → CHECKED → CLOSED
                                           ↓
                                      EXCEPTION → RESOLVED
```

关键约束：

- `PREALERTED` 后允许补充明细，但必须增加版本并记录操作者。
- `SEALED` 后锁定预期清单；临时增删只能通过更正单或异常单。
- `DEPARTED` 表示车辆/承运资源实际离开起点，不能仅凭“已配发”推断。
- `ARRIVED` 只表示到达，必须通过总包或邮件勾核后才能 `CHECKED`。
- 发生少件、超件、错包、封签不符、重量差异时进入 `EXCEPTION`，差异处理完成后才可关闭。

### 5.2 事件与状态的边界

状态是当前汇总结果，事件是不可变事实。建议由事件驱动状态变化：

| 事件 | 主要对象 | 状态影响 |
|---|---|---|
| `MANIFEST_PREALERT` | 路单 | `DRAFT → PREALERTED` |
| `VEHICLE_IN` | 运输任务/机构 | 记录车辆进局 |
| `MANIFEST_SEALED` | 路单 | `PREALERTED → SEALED` |
| `VEHICLE_DEPARTED` | 运输任务 | 路单可转 `DEPARTED` |
| `VEHICLE_ARRIVED` | 运输任务/机构 | 路单转 `ARRIVED` |
| `UNLOAD_COMPLETED` | 总包/运输任务 | 允许开始勾核 |
| `MANIFEST_CHECKED` | 路单 | 差异为零时转 `CHECKED` |
| `DISCREPANCY_OPENED` | 路单/总包/邮件 | 转 `EXCEPTION` |
| `MANIFEST_CLOSED` | 路单 | 归档，禁止修改历史事实 |

## 6 对真实案例的映射

### 6.1 RD588151315CN 的建议建模

| 轨迹事实 | 对象 | 关键关联 |
|---|---|---|
| RD588151315CN | 邮件 | `mail.mail_no` |
| 总包 0057 | 总包 | `total_package.package_no=510620025104003412220057000220` |
| 交接对象 3351007039 | 运输/交接对象 | `handoff_record.external_reference` |
| 路单流水号 07200001 | 路单运行批次 | `manifest.manifest_serial_no` |
| 总包 0006 | 新总包 | 与 0057 通过开拆/再封装事件关联 |
| 路单流水号 07230001 | 干线路单 | 关联广州-乌市运输任务和豫 LB6886 |
| 乌市路单 52 | 下一段路单 | 起点乌鲁木齐中心，终点乌鲁木齐国际互换局 |

邮件在广州国际开拆后不再直接属于 0057；它通过拆包事件进入 0006，随后通过路单 07230001 运输。这样既能查询邮件轨迹，也能回答“某个路单上有哪些总包”“某个总包在哪一次交接中少件”。

### 6.2 进口互换局记录的建议建模

“进口邮件直封开拆”对应总包入站事件和 `package_item_line.UNPACK`；“进口邮件互封封发”对应新总包生成、邮件装载和 `REPACK`；“处理中心车辆进局/解车/路单接收勾核”对应运输任务和路单事件；“海关待验、征税、寄达地补录”属于邮件处理或海关业务事件。这样可避免把海关状态、邮件状态和路单状态混为一体。

## 7 本科毕设可落地的改造方案

### 7.1 第一阶段 必做

1. 保留现有 `sorting_manifest` 作为路单主表，新增 `manifest_serial_no`、`handoff_mode`、`sealed_at`、`departed_at`、`arrived_at`、`checked_at`、`version_no` 和标准化状态。
2. 保留并强化 `sorting_manifest_package`，把总包作为路单的一级明细；沿用已有的 `expected_weight`、`actual_weight`、`seal_no`、`received_at`，补充 `discrepancy_status` 与历史关联。
3. 沿用现有从 `dispatch_bag.mail_no_list` 向 `sorting_manifest_item` 同步的逻辑，改为以关系表和不可变事件作为查询及勾核依据；避免把单一 `sorting_total_package.manifest_no` 当成全程历史。
4. 在 dispatch 与 sorting 之间传递稳定的 `manifestNo`、`manifestSerialNo`、`transportTaskCode`，不再只依赖 `M + batchNo` 推导。
5. 增加路单事件表或复用 tracking event，至少支持预告、封车、离开、到达、解车、勾核、关闭和异常。
6. 统一差异类型：`MISSING_PACKAGE`、`SURPLUS_PACKAGE`、`MISSING_ITEM`、`SURPLUS_ITEM`、`WEIGHT_MISMATCH`、`SEAL_MISMATCH`。

### 7.2 第二阶段 可选增强

- 增加 `manifest_alias` 保存发送端号码、接收端号码、外部系统号码。
- 以 JSON 保存原始内网详情，但业务查询使用结构化字段。
- 增加总包拆分、合并、改封和跨路单转移的关系事件。
- 增加运输任务与路单的多对多关联及派车单、车牌、承运商字段。
- 在前端详情页增加“路单摘要、总包清单、邮件清单、事件时间线、差异处理”五个区域。

### 7.3 暂不建议纳入毕设范围

不建议在本科毕设中模拟完整海关报文、真实航空/船运订舱、GPS 实时轨迹、跨境外部邮政系统接口和复杂计费结算。这些内容会显著扩大边界，却不能直接证明路单建模是否正确。用事件类型和外部引用字段保留扩展点即可。

## 8 推荐的数据完整性规则

1. `manifest_no`、`package_no`、`mail_no` 分别建立唯一性约束，不互相复用；`manifest_serial_no` 按机构和业务日期组合约束，不单列全局唯一。
2. 一个路单只能有一个起点和接收终点；改道通过新版本或新路单表达。
3. 路单关闭前，所有预期总包必须处于 `RECEIVED`、`MISSING` 或 `SURPLUS` 等明确状态，不能以“未扫描”自动判定遗失。
4. 实收数量、重量应从明细汇总；手工修正必须记录人员、原因和时间。
5. 所有事件保留 `occurred_at` 和 `recorded_at`，支持离线补传和时钟差异。
6. 接口采用幂等键，重复车辆进局、重复勾核不会生成重复事实。
7. 跨服务只传稳定业务编码，不能假设不同数据库的自增 ID 相等。
8. 业务名称与机构名称可以变化，机构编码、总包条码和邮件号不能因改名而变化。

## 9 结论

本系统最合理的路单模型是“路单作为一次交接的清单和批次，总包作为一级明细，邮件作为二级明细，运输任务作为执行资源，事件作为事实记录”。这个模型能够解释用户提供的两组真实轨迹：同一邮件多次换总包和换路单、同一运输任务承载多个总包、发送端与接收端存在本地号码差异，以及车辆进局、解车、勾核与开拆封发属于不同业务层。

对本科毕设而言，先把稳定主键、明细关系、生命周期、差异核对和事件时间线做正确，就足以形成清晰的业务闭环。后续再通过别名、版本、运输任务多对多关系和外部原始详情扩展，不需要推倒现有 dispatch、sorting 和 tracking 模块。

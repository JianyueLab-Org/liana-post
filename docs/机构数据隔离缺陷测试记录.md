# 机构数据隔离缺陷测试记录

记录日期：2026-11-12  
测试环境：Liana Post Docker 演示环境  
测试类型：缺陷复现、修复验证与回归测试

## 测试目的

验证普通营业员只能查看和操作与其所属机构相关的派送批次、邮袋及待接收总包，避免通过列表接口或伪造请求参数访问其他邮局的数据。管理员保留跨机构查看能力。

## 缺陷案例

### DSI-01 派送批次列表跨机构可见

**复现步骤：** 使用 `LN-OR-01` 的营业员登录，打开“批次管理”。  
**修复前结果：** 批次列表及待编批总包列表由接口全量返回，能够看到与 Oro 无关的 B1 数据。  
**原因：** `/api/dispatch/batches` 与 `/api/dispatch/bags` 未从登录令牌读取机构范围，直接查询并返回全库数据。  
**修复：** 普通员工只返回起点或终点属于本机构的邮袋及其批次；批次响应只包含当前用户可见的袋号。创建和审批批次另行校验起点机构。管理员仍可查看全部。  
**验证：** `DispatchServiceImplScopeTest` 覆盖机构列表过滤和阻止营业员使用 B1 邮袋创建批次。

### DSI-02 待接收退回总包跨机构可见及可操作

**复现步骤：** 使用 Oro 营业员登录，打开“接收总包”。演示库中存在目标标记为 `RETURN_ORIGIN`、原寄局为 B1 的包裹。  
**修复前结果：** 页面能够列出其他邮局的待接收包裹；接收接口还使用请求体传入的机构编码，存在伪造机构编码后执行接收的风险。  
**原因：** `/api/oms/packages` 将所有带 `package_id` 的邮件全量聚合；没有按目的网点过滤。`RETURN_ORIGIN` 也没有解析为原寄局。接收接口信任客户端提交的 `currentFacilityCode`。  
**修复：** 列表接口依据 JWT 中的机构编码过滤。普通营业员提交的机构编码不参与授权判断；接收操作使用令牌机构，并再次检查包内全部邮件的目的网点。`RETURN_ORIGIN` 按邮件原寄局匹配，含其他机构邮件的混合包裹拒绝接收。  
**验证：** `OmsServiceImplTest.packageReceptionUsesDestinationAndReturnOrigin` 覆盖 Oro/B1 目的网点过滤、退回原寄局解析及跨机构接收拒绝。演示环境使用 Oro 会话打开“接收总包”，页面显示“当前没有可接收的总包”。

# 数据库设计与变更规范

状态：2026-11-18，九库 Flyway 基线、必需数据、独立 demo 种子和显式初始化入口已建立并接入正式演示 Compose；P1 已增加预告版本、本地 outbox、结构化装包和 OMS 确认，sorting V3/V4 封单/作废回执、dispatch V4/V5 可靠投递，以及 dispatch V6 / transport V2 整单分配、有效占用与取消释放历史，P2 sorting V5 / dispatch V7 / transport V3 增加包级实收、接收位置及双端确认，本轮增加 sorting V6 / dispatch V8 同包多段预约、有效批次关系和历史回执。正式演示 Compose 已切换到统一 database-init、Nacos 就绪依赖和独立 v2 数据卷；验证记录见 [数据库使用说明](../database/README.md)。实施顺序见 [路单与数据库整合开发计划](manifest-database-redesign-plan.md)。

## 1. 适用边界

本轮新增结构登记：sorting V7/V8 的开拆/重封请求及逐件来源、OMS V4 开拆 inbox、dispatch V9 重封 inbox/来源。字段清单已同步，MySQL 8 与实际服务验收尚待进行；这些新增迁移不代表现行 demo 初始化路径已切换。

2026-11-17 收尾更新：sorting V9 的勾核/关闭及双端 outbox、dispatch V10/transport V4 的关闭 inbox 已登记；87 张业务表、752 列与独立 MySQL 8 实际结构一致。九库首次/重复迁移及种子保护回归通过，实际服务与浏览器验收另见 database/verification.md。上述阶段记录中的“尚待 MySQL”由本次结果更新；现行 demo 初始化入口仍未切换。

本系统是 Liana Pacific 海岛邮政模拟系统。用户已允许放弃原有演示数据，因此本次采用空库重建，不安排历史业务数据迁移、旧编号映射或双写兼容。允许舍弃旧数据不代表允许破坏新模型运行后形成的运输、交接、开拆和邮资交易历史。

保留现有服务与数据库边界，不合并为一个大库，不为统一外观批量重命名全部旧表。本规范用于新增表、被本轮改造的字段以及统一初始化工程；其他现存差异登记后逐步治理。

所有 SQL、配置及文档使用 UTF-8 无 BOM、LF。禁止将数据库客户端导出的含业务记录、`DROP TABLE`、历史自增值和关闭外键检查的转储文件作为新的初始化基线。

## 2. 服务所有权

| 数据库 | 唯一业务写入方 | 主要职责 |
|---|---|---|
| `auth_db` | auth | 用户、角色、权限和所属机构 |
| `facility_db` | facility | 机构、邮政网络边、海岛及服务覆盖主数据 |
| `oms_db` | OMS | 邮件、寄收件人、产品及收寄业务 |
| `dispatch_db` | dispatch | 封装总包、邮件装包关系、站内配发批次和交出操作 |
| `sorting_db` | sorting | 路单主数据、预期清单版本、接收勾核、开拆记录 |
| `transport_db` | transport | 运力、执行路线、班次、运输任务及任务分配历史 |
| `tracking_db` | tracking | 面向查询的轨迹投影 |
| `syncer_db` | syncer | 同步调度及重试管理，不充当其他服务的业务库 |
| `postage_db` | postage | 资费版本、报价、零售凭证和邮资核销 |

跨服务传递稳定业务编码，不假设各库自增 ID 相同。禁止业务服务跨库直接更新或建立跨库外键。跨库关联通过服务接口或持久化事件完成；部署后的联调核查脚本可以跨库只读检查，不能成为运行依赖。

dispatch 的封装记录和 sorting 的入站处理记录是不同职责下的事实。接收方不能通过更新发送方记录完成勾核；两处出现同一个总包条码时，应明确区分主事实、接收事实及可重建投影。路单只能由 sorting 应用服务写入，dispatch 发出创建/预告请求，transport 提供执行事实。

## 3. 唯一结构来源与版本管理

目标目录固定为：

```text
database/
  README.md                         # 实际命令、依赖及重建边界
  inventory.md                      # 表、字段、来源、所有者和治理状态
  migrations/
    auth_db/V1__baseline.sql
    facility_db/V1__baseline.sql
    ...                             # 九个库分别维护版本
    sorting_db/V2__manifest_prealert_versions.sql
    dispatch_db/V2__manifest_reference_and_outbox.sql
  seeds/demo/v1/                     # 海岛主数据及虚构演示配置
  scenarios/                        # 通过业务接口建立的可重复演示场景
  checks/                           # 结构、约束、引用及场景核查
```

基线、种子、核查、清单和统一入口已建立；`scenarios/` 和后续路单模型迁移随 P1—P4 交付。各库版本独立，无必需数据的 sorting/dispatch 库将 V2 用于首批领域迁移，不要求各库同号版本用途相同。

统一采用 **Flyway 版本化 SQL**。通过根工程专用 Maven profile 和显式初始化任务执行，不由业务服务启动时自动迁移。实施时在父 POM 固定插件及 MySQL 支持依赖版本，并在 MySQL 8 空库验证；不使用浮动版本。各库使用自己的 `flyway_schema_history`，执行顺序写在统一入口中，不再按整个目录文件名猜测跨库顺序。

- `V1__baseline.sql`：审计后的当前结构，不夹带历史业务行。
- `V2__system_reference.sql`：服务正常运行必需的锁行、字典、规则初始值等；没有此类数据的库可以跳过该版本。
- 后续 `Vn__description.sql`：本轮路单及未来结构变更。已执行并纳入版本管理的脚本禁止原地修改，通过新版本更正。
- `baselineOnMigrate` 保持关闭。旧演示库不自动标记为已迁移，不用 `repair` 掩盖校验和差异。
- MySQL DDL 不保证整批事务回滚。执行失败即停止；空库验证失败重建隔离测试库，已投入使用的新库通过明确修复脚本处理。

根目录 `db/`、`db_revise/`、服务主资源目录的 MySQL 初始化 SQL 已从工作树删除；Git 提交 `9052993` 保留历史查阅点。以后只使用 `database/migrations`、`database/seeds` 和显式初始化入口。服务所需 H2 测试 DDL 可留在独立测试目录，标注其对应迁移版本；不能作为另一套 MySQL 权威结构。

## 4. 初始化、种子与重建

统一初始化流程为：创建目标库 → 逐库迁移及校验 → 导入必要配置 → 按需导入 demo → 检查 → 允许业务服务启动。

业务服务正常启动保持 `SPRING_SQL_INIT_MODE=never`，同时清理 Java 构造器、启动回调及管理接口中隐式建表、清库、创建演示业务数据的行为。不能只关闭 Spring SQL 初始化而保留其他入口。

数据分四类处理：

| 类别 | 内容 | 规则 |
|---|---|---|
| 系统必需数据 | 并发锁单例、产品/状态字典、必要权限定义 | 版本化初始化，不随 demo 开关缺失 |
| 可运营配置 | 初始资费目录、发行规则等 | 显式引导导入；已有管理员修订不得被重启覆盖 |
| 海岛演示主数据 | LN 机构、账号与角色分配、邮路、运力、班次 | 仅 demo 环境导入；通过业务编码关联 |
| 演示业务过程 | 邮件、总包、路单、交接、扫描、邮资交易 | 首选场景脚本调用业务接口生成；不恢复旧运行记录 |

演示种子使用明确版本及校验和，在各目标库的 `demo_seed_history` 留下成功记录；同版本重复执行只校验并跳过，内容变化要求新版本或重建。中途失败停止引导，不把半套演示网络标记成功；可重试步骤按业务唯一键幂等，不覆盖已人工修改的数据。测试数据只进入隔离测试库。

新建空 MySQL 卷和已有卷的增量迁移必须调用同一迁移入口，不能仅依赖 `/docker-entrypoint-initdb.d`。Compose 的独立初始化任务成功后，业务服务才就绪。邮资的单独 `postage-db-init` 并入该入口，保留其三个现行 schema 涉及的全部功能。

“初始化/迁移”不执行删除。“重建 demo”是另一个显式命令：列明目标连接、九个允许重建的库及外部状态清理范围，拒绝未知连接或库名，禁止默认执行 `docker compose down -v`。Redis、同步队列及浏览器缓存中的旧业务引用也要按实际命名空间清理，不能清空共享 Redis。当前 Compose MySQL 暴露端口是 3307，但工具应读取实际配置，不能误连默认 3306。

## 5. 命名、类型和单位

新增表、字段、索引使用英文小写 `snake_case`。表名沿用服务领域前缀；主键 `id`，业务编号 `*_no`，稳定配置编码 `*_code`，本库真实外键 `*_id`，数量 `*_count`，时间点 `*_at`，布尔值 `is_*`。现存的 `origin_facility_id` 若实际存机构编码，应在相关接口和模型改造时同步改为 `origin_facility_code`。

| 数据 | 新增或改造字段的默认约定 |
|---|---|
| 内部主键 | `BIGINT` 自增，Java `Long`；不向跨服务接口暴露作业务标识 |
| 机构、路线、规则编码 | `VARCHAR(64)`；`facility_route_code`、`dispatch_rule_code`、`transport_route_code` 各自独立 |
| 路单、总包、任务业务号 | `VARCHAR(64)`，各自唯一且类型明确 |
| UPU 邮件号 | 保持业务校验的 13 字符；不能向此字段写总包号或路单号 |
| 状态、差异类型 | `VARCHAR(32)`，服务端枚举校验；不保存中文显示文本 |
| 操作人 | 从认证身份取得稳定用户标识；既有数字用户 ID 在事件契约中使用明确的字符串表示，默认 `VARCHAR(64)` |
| 重量 | 总包、邮件使用 `weight_grams`；需小数精度时 `DECIMAL(14,3)`，不暗中四舍五入 |
| 运力 | `capacity_grams`，足够范围的整数或精确小数；旧 kg 字段只能在明确转换边界保留 |
| 金额 | `DECIMAL(12,2)` + `currency_code`，Java `BigDecimal`；Liana 使用 LNR |
| 版本 | `version_no` 表示清单版本；并发控制单独使用 `lock_version`，不混用 |

配置编码生成和输入统一为大写 ASCII、去首尾空白，业务号按各自格式校验，不任意截断。标识列显式使用大小写敏感比较（如 `utf8mb4_bin`），名称等文本默认 `utf8mb4_unicode_ci`。在改动已有列排序规则前检查重复业务键，不能仅靠大小写变化区分同一编码。

未知重量用 `NULL` 并记录来源，0 只能表示真实零值；演示估重须标记 `weight_source=ESTIMATED` 和估算规则，不能继续把“每件 100g”或“每件重量 1”当作实测重量。数量非负，来源明确；汇总值从明细计算，缓存汇总须可核对。

不以统一规范为由转换邮资模块已有的 UUID/字符串主键、UTC 毫秒 `BIGINT` 时间、`VARCHAR(128)` 操作人及 JSON 文本快照。这些是登记在册的现有契约；只有实际业务需求和相应测试支持时才单独变更。

## 6. 时间与业务日

新增及本轮改造的普通业务时间统一为 UTC，MySQL 使用 `DATETIME(3)`，连接与会话时区为 `+00:00`，Java 优先使用 `Instant`；若使用 `LocalDateTime` 必须显式按 UTC 转换。`DATETIME` 本身不保存时区。接口使用带 `Z` 或明确偏移的 ISO 8601 时间，不发送含义不明的本地时间。

邮资模块保留 UTC epoch milliseconds，通过接口适配成同一时间语义。历史表若暂未转换，在字段清单中登记实际语义，不把旧 `+08:00` 数值直接当作 UTC。调整服务器、JDBC、实体映射及序列化必须一起验证，不能只替换 `serverTimezone`。

Liana 业务日按固定 `+12:00` 计算；`Pacific/Liana` 仅为世界观标签，不能传给真实 IANA 时区解析器。路单流水号的业务日期在开立时固定，跨日到达或离线补传不得重算。班次本地发车时刻应保存本地时刻、业务时区语义及生效规则，不混同已发生事件的 UTC 时间。

事件至少含 `occurred_at` 和 `recorded_at`：前者为业务发生时间，后者为服务接收时间。离线重传保留发生时间；状态不能简单按“最后收到的一条事件”覆盖，需校验事件编号、对象版本及合法流转。

## 7. 约束、历史及事务

- 所有业务表使用 InnoDB。必填业务键 `NOT NULL` 并建唯一索引；本库强从属关系使用外键，历史数据删除默认 `RESTRICT`，不级联删除审计事实。
- 机构停用、规则失效通过状态或生效区间表示。不是每张表都加逻辑删除；事实、已封清单及交易记录不得用删除隐藏。
- 关系用结构化明细表表达。JSON 用于不可变版本快照、请求摘要、配置和扩展信息；不能用 JSON 邮件列表替代需要约束的装包关系。
- 路单版本保存完整头信息与明细快照或可完整重建的版本明细。仅 `version_no + hash` 不算保留历史内容。
- 总包在不同路段多次运输，使用 `bag_no + manifest_no` 关联。删除全局 `UNIQUE(dispatch_bag_id)` 的同时建立有效占用约束，不能简单放开为无限制重复运输。
- 建议在 sorting 使用以 `bag_no` 为唯一键的当前交接占用表，关联路单并保存并发版本；交出前校验上一段已接收、总包未开拆、当前位置及发送机构匹配，结束后释放占用。历史明细始终保留。
- transport 使用以 `manifest_no` 为唯一键的当前分配表，以及追加保存的任务分配历史。取消/改派结束旧有效分配，不能删掉旧任务或改写原关联。跨服务确认采用持久化待确认状态、幂等命令及重试；任一方未确认时禁止发运。
- 唯一约束必须覆盖并发，而非仅“先查询再插入”。更新使用条件状态与版本，检查受影响行数；流程事务内不等待远程 HTTP。

幂等台账至少记录作用域、请求键、请求摘要、处理状态和可重放响应。同键同内容重试返回原结果，同键不同内容拒绝。客户端完成开拆请求在首次提交前固定幂等键，网络重试不能重新生成。

跨服务事件由产生业务事实的服务在**同一个本库事务**写入业务表及 outbox。不能将 dispatch 事务和 `syncer_db.outbox_message` 的远程写入视为原子提交。消费端建立 inbox/已处理事件唯一约束，支持重复、乱序、离线重放及人工重试。tracking 是投影，发送失败不得撤销已经发生的运输事实。

查询索引围绕实际接口建立，例如 `(destination_facility_code, status, created_at, id)`、`(manifest_no, bag_no)`、`(bag_no, received_at)` 和 outbox 待发送时间。不要给所有字段机械建索引；列表分页须有稳定排序和机构权限条件。

## 8. 变更交付规则

每次数据库相关变更同时提交：版本化 SQL、字段/所有者清单更新、实体及接口调整、种子和场景调整、必要验证。明确它需要空库重建还是支持新基线后的增量升级。不能只提交一段临时 SQL，事后补到另一份 schema。

切换统一入口前必须通过：

1. MySQL 8 隔离空库完整创建九库；首次初始化、二次迁移、重启均不多造演示邮件、不覆盖配置。
2. 所有主业务表、列、默认值、索引、外键、必需锁行和字典与代码清单匹配；没有依赖未执行的旧补丁。
3. 初始账号登录、LN 机构授权、收寄、路由、分拣、运输、轨迹、同步和邮资核心流程可用。
4. 并发唯一约束、幂等冲突、时间跨日、小数重量、同包多段与取消改派在真实 MySQL 验证。H2 测试不能代替这些验证。
5. 初始化与 demo 重建命令分离；任何旧入口均不再被默认部署命令引用。

验证通过才切换 Compose 并归档旧入口。回退以代码版本和隔离演示库快照/重建为单位，不承诺跨九库 DDL 的自动事务回滚。

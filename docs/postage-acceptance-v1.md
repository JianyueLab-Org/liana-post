# 逐件收寄与邮资核销 v1

## 已确认业务规则

- 首版仅工作人员代客购买与收寄。每件邮件独立结算，批量统一结算暂不实现。
- 一张数码邮票只能完整、一次性用于一件邮件；同件可组合多张数码邮票和传统邮票。超额记录为溢贴，不找零、不保留余额。
- 传统邮票按“面额 × 张数”登记，营业员必须人工鉴别并确认已贴用。系统计算金额并保存记录，无法电子鉴别实物真伪或阻止同一实物再次登记。
- 不足额时先确认收到差额现金，复用零售售卖、收款、发行接口，取得数码邮票后贴用。补购是一笔独立零售：收寄失败不退款、不撤销已购邮票。售卖失败或恢复期间请核对柜台现金，不要重复收款。
- 信函 U 不选附加服务使用 UU 运单；加 REGISTRATION 使用 RR 运单及挂号费。旧 R 产品仍兼容挂号信。物流状态仍为 CREATED，交易状态不替代物流状态。

## 流程与恢复

1. OMS 校验工作人员、网点、产品、重量、目的地及寄递服务；邮资服务生成报价。
2. 客户端核对代码及传统邮票，金额预览仅供参考。
3. 邮资服务在本地事务内重新校验报价有效性、操作员及邮件计价条件，按代码顺序锁邮票，计算邮资。保存 PREPARED 结算、传统邮票记录、计价快照引用和审计，邮票变为 RESERVED。
4. OMS 读取邮资服务的权威记录，在同一个 OMS 本地事务内写入邮件与幂等台账 CREATED。客户端不能提交金额或伪造已结清状态。
5. 邮资服务收到原运单号后，在本地事务内把结算改为 COMPLETED，邮票改为 REDEEMED，并写审计。

两个服务仍使用各自数据库。HTTP 调用不持有数据库事务或行锁；没有引入消息队列或分布式事务。首版预占使用共享锁行串行化请求编号及报价校验，优先保证正确性，后续需要提高吞吐时再优化。

网络失败、OMS 失败或核销事务失败保留 PREPARED/RESERVED。工作人员在收寄页面或“收寄结算”页面恢复原请求。OMS 已提交但响应丢失时，台账返回同一运单，邮资服务继续完成核销。已预占记录使用原计价依据，之后的报价到期、邮票到期或调价不重算这笔结算；OMS 创建前仍检查收寄条件。

取消必须先让 OMS 在本地事务内写入 CANCELLED 台账，阻挡延迟到达的创建请求，然后才能释放 RESERVED 邮票。创建已提交则返回原运单并完成核销，取消不能撤销已收寄邮件。无自动超时释放；人工取消需先确认实际业务。已取消结算不可复用原报价，需要新报价及新请求编号。

浏览器仅持久化收寄请求编号、结算编号和补购售卖请求信息，不缓存邮件身份、地址或邮票代码。刷新后按原编号查询；尚未找到记录时允许重新录入，但保留原请求编号，服务端拒绝该编号对应不同业务。尚未确认的请求不要另开页面发起新业务。

## 接口与权限

网关前缀 `/liana-postage-service`，业务前缀 `/api/postage`：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/acceptances` | `{requestId,quoteId,mail,stampCodes,traditionalStamps,traditionalConfirmed}`，预占并收寄 |
| GET | `/acceptances?page=0` | 每页 20 条，本人记录；管理员全部 |
| GET | `/acceptances/{id}` | 本人或管理员完整结算与邮票 |
| GET | `/acceptances/by-request/{requestId}` | 按当前工作人员请求编号恢复 |
| GET | `/acceptances/by-waybill/{waybill}` | 柜台工作人员查金额、传统邮票和计价依据；不返回完整代码及收寄个人资料 |
| POST | `/acceptances/{id}/resume` | 继续原收寄和核销 |
| POST | `/acceptances/{id}/cancel` | OMS 确认取消后释放预占；已创建邮件完成核销 |

OMS 网关前缀 `/liana-oms-service`，业务路径 `/api/oms/acceptances/validate`、`/{id}/complete`、`/{id}/abort`。complete/abort 只接收结算编号，OMS 自行读取权威记录；用于服务协作与幂等恢复。

所有新增接口验证实际 JWT 签名。ADMIN，或同时具有 MAIL_CREATE 的 CLERK/MANAGER 可操作；完整结算恢复仅本人/管理员。作废仍仅管理员，RESERVED/REDEEMED 不允许作废。403/409 不代表可以重复收款。

**接口兼容变更：原 POST `/api/oms/mails` 返回 409，要求走邮资结算入口，避免绕过核销创建邮件。** liana-web 已迁移。外部客户端须改为“校验、报价、结算”；旧 `script/smoke_test.py` 物流脚本须传 `--waybill-no` 使用已有邮件，新收寄联调使用 `script/postage_acceptance_smoke.py`。读取邮件及已有物流接口保留。历史邮件显示“暂无邮资结算记录”，不补扣邮资，也不推断历史支付状态。

## 升级与限制

已有 MySQL 环境分别执行：

- postage_db：`liana-postage-service/src/main/resources/acceptance-schema.sql`（须先具备资费、零售表）。新增预占锁、结算及邮票关系三张表。
- oms_db：`db_revise/20261014_postage_acceptance.sql`。新增 OMS 幂等台账。也可在 oms_db 执行 `liana-oms-service/src/main/resources/acceptance-schema.sql`。

均为可重复执行的加表 SQL，不清库、不改历史邮件。Docker 新建环境及 postage-db-init 已包含邮资新增表；已有 OMS 数据卷需要单独执行 OMS 升级 SQL。随后同时升级邮资、OMS、liana-web，升级期间暂停柜台收寄。运行时已有资费不被种子覆盖。

OMS 轨迹 ACCEPTED 与缓存清理改为邮件事务提交后触发，避免回滚邮件产生已收寄轨迹。轨迹仍沿用现有尽力发送机制，没有可靠消息台账；轨迹服务失败需要后续查询与补录，不能承诺必达。已核销邮件的撤销、退款、重新发行、批量结算及线上支付不在本轮范围内。

## 验证

后端 85 项指定测试：邮资 73（含核销及兼容 11），OMS 12（含收寄 7）；前端 15 项与生产构建。核销测试覆盖组合与溢贴、不足额/重复代码、报价与身份边界、同请求并发、同邮票竞争、响应丢失恢复、取消与创建竞争、审计写入失败时整体回滚及重试。OMS 测试覆盖业务与权限校验、取消台账阻挡迟到创建、重复请求返回原运单。严格解析器可读取现有 Result 的 success/fail 响应元数据，收寄请求仍拒绝未知字段。旧 R 报价即使未显式记录附加服务列表，也按隐含挂号匹配规范化收寄内容；不修改原报价快照。

`script/postage_acceptance_smoke.py` 在本地演示环境生成带标记的测试售卖和邮件，验证真实 MySQL/网关/服务间调用。它会写演示业务数据并记录模拟柜台现金，不接真实支付；不会删除测试数据或输出 JWT、邮票代码。运行参数及实测结果见脚本说明。

2026-10-14 本地 Docker / MySQL 8 实测 7 组场景通过，测试标记 `acceptance-smoke-ca9d431a`：传统贴用 2.80/应付 1.50/溢贴 1.30；传统 0.80 + 数码 1.00/溢贴 0.30；六次同请求并发只核销一次；不足额拒绝后补购 0.70 再结算；U 加挂号应付 4.50 并生成 RR 运单；六个不同请求竞争一张邮票仅一件成功；小数重量、禁邮目的地和权限校验。数据库检查得到 5 笔 COMPLETED、5 笔 OMS CREATED 台账及 5 条对应邮件，新业务表均为 InnoDB。

浏览器实际页面已检查：0.80/1.50 显示 0.70 差额及现金确认入口；结算详情显示组合金额、溢贴及“已保存计价快照”，未把历史结算标记为过期报价。补购发行和核销写操作由本地 HTTP 联调验证，页面核对、查询与金额展示通过浏览器验证。异常响应丢失及审计失败回滚采用隔离测试模拟，不宣称已在真实服务中实施这些故障。

最终版本补充实测：旧 R 报价的附加服务列表为空时，规范化挂号邮件仍可足额结算，原快照保留，生成 `RR670260352LN`；实际邮件详情保留 CREATED 状态，显示已收寄轨迹及组合邮资结算。
